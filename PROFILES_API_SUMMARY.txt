ENDPOINTS IMPLEMENTES
===============================================================================

GET /api/profiles
  - Liste les profils du user connecte
  - Headers: Authorization: Bearer <token>

POST /api/profiles
  - Cree un nouveau profil (OWNER, PRODUCER, BUYER, INVESTOR, PROVIDER)
  - Headers: Authorization: Bearer <token>
  - Body: { type, displayName, region?, commune?, activityArea?, ... }
  - Met hasCompletedOnboarding = true si premier profil

GET /api/profiles/[id]
  - Details d'un profil specifique
  - Headers: Authorization: Bearer <token>

PATCH /api/profiles/[id]
  - Modifie un profil existant (ownership verifie)
  - Headers: Authorization: Bearer <token>
  - Body: { displayName?, bio?, region?, phoneVisible?, ... }

DELETE /api/profiles/[id]
  - Soft delete (isActive = false)
  - Headers: Authorization: Bearer <token>
  - Interdit si dernier profil actif


REGLES DE GESTION IMPLEMENTEES
===============================================================================

1. Un User peut avoir max 1 Profile de chaque type
   - Contrainte Prisma @@unique([userId, type])
   - Verification avant insertion
   - Erreur 409 si doublon

2. hasCompletedOnboarding = true au premier profil
   - Mis a jour automatiquement lors du POST /api/profiles

3. Champs obligatoires variables selon le type
   OWNER:     displayName, region, commune
   PRODUCER:  displayName, activityArea, region
   BUYER:     displayName
   INVESTOR:  displayName
   PROVIDER:  displayName, activityArea

4. Soft delete (isActive = false)
   - DELETE /api/profiles/[id] desactive au lieu de supprimer
   - Conservation de la tracabilite
   - Relations preservees

5. Conservation d'au moins 1 profil actif
   - Impossible de supprimer le dernier profil
   - Erreur 400 Bad Request si tentative

6. Ownership verifie
   - Un user ne peut acceder qu'a ses propres profils
   - Erreur 403 Forbidden si tentative d'acces

7. Header X-Active-Profile requis pour actions metier
   - Le frontend envoie le profil actif dans chaque requete
   - Verifie par les middleware withAuth / withProfile


MIDDLEWARE REUTILISABLES
===============================================================================

withAuth(handler)
  - Wrapper pour routes necessitant une authentification
  - Recupere user + profil actif (header X-Active-Profile)
  - Gestion d'erreurs automatique

  Exemple:
  export const GET = withAuth(async (req, ctx) => {
    // ctx.user, ctx.profile disponibles
  });

withProfile(type, handler)
  - Wrapper pour routes necessitant un type de profil specifique
  - Verifie que ctx.profile.type === type requis
  - Erreur 403 si mauvais type

  Exemple:
  export const POST = withProfile("OWNER", async (req, ctx) => {
    // ctx.profile est garanti etre un profil OWNER
  });

withOptionalAuth(handler)
  - Wrapper pour routes publiques avec auth optionnelle
  - ctx.user peut etre null

  Exemple:
  export const GET = withOptionalAuth(async (req, ctx) => {
    if (ctx.user) {
      // User connecte
    } else {
      // Utilisateur anonyme
    }
  });
